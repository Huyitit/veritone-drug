# /apply_gql_sdk — rewire a spec's raw GraphQL onto the generated SDK

Invocation syntax: `apply_gql_sdk <filePath>`

- `filePath`: the citest spec file to rewrite — usually a
  `citest/tools/graphql-api/test/<area>/*.spec.ts` file — that still calls
  `client.query(<raw string>, ...)` / `gqlClient.query(<raw string>, ...)` instead of the
  generated SDK.

`filePath` may be given relative to the repo root, relative to
`services/api/core-graphql-server`, or as a bare filename (resolve by searching under
`citest/tools/graphql-api/test/` and `citest/obsolete/` if the exact path isn't found).

## Hard constraint: write scope

This skill may only modify `filePath` itself. Never create, edit, or otherwise touch any other
file — not `citest/tools/graphql-api/src/gql/gql.ts` (the generated SDK; it is regenerated by
graphql-codegen and must never be hand-edited), not
`citest/tools/graphql-api/src/queries/extracted/*` (that's the `add-gql-sdk` skill's job, a
different helper layer), nothing else. If making an operation SDK-compatible would require
changing anything outside `filePath`, skip that operation instead and say why.

## Background: which "SDK" this targets

- `citest/tools/graphql-api/src/gql/gql.ts` — the **generated** SDK (graphql-codegen). Exposes
  `getSdk(client)` → an object of methods, one per named operation, e.g.
  `sdk.me(...)`, `sdk.createApplication(variables)`, `sdk.deleteUser(variables)`. Each method
  returns `Promise<{ data: <OperationName>Query | <OperationName>Mutation, errors?, extensions?,
  headers, status }>` — the payload is under `.data`, not flat. This is what this skill migrates
  *to*.
- `citest/tools/graphql-api/src/queries/extracted/*.ts` — hand-maintained `gql`-tagged constants
  used via `client.query(SOME_EXPORT, variables)`. Not this skill's concern in either direction;
  a raw string that could only be served by adding a new extracted helper (no generated SDK
  method exists) is out of scope here — that's `add-gql-sdk`'s job, not this skill's.

## Step 1 — Read the input and learn the client's call conventions

1. Read `filePath` in full.
2. Note how the GraphQL client is obtained/typed in this file (e.g. `GraphqlClient` from
   `../../src/graphqlUtil`) — it exposes both `.query(...)` (raw/extracted-helper path) and
   `.sdk.<op>(...)` (generated path). If the file already uses `.sdk.` elsewhere, match that
   existing style for requestHeaders/variables shape.

## Step 2 — Find every raw inline GraphQL call

Find every `.query(<literal template string>, ...)` call (e.g. `gqlClient.query(\`query {
...}\`)`, `client.query(\`mutation { ... }\`, null)`) where the first argument is a literal
template string written inline at the call site — not an imported `gql`-tagged constant, and
not already an `.sdk.<op>(...)` call. Those are the only candidates; anything already
helper/SDK-backed is out of scope.

For each candidate, parse:
- **Operation type**: `query` or `mutation`.
- **Top-level selections**: every field selected directly under the operation (before
  descending into nested selections). This matters for Step 3.
- **Root field name**: the single top-level field's name (or the operation's own name if it's
  explicitly named, e.g. `mutation updateOpenIdProvider { ... }` — in this repo's generated SDK,
  operation names and their sole root field consistently match, so either gives the same
  answer).
- **Arguments**: literal values, JS template interpolations (`` `id: "${connectId}"` ``), and
  any already-declared `$variables`.
- **How the result is consumed**: every place the call's return value feeds into (`_.get(result,
  'rootField...')`, `result.rootField`, destructuring, `.rejects.toThrow(...)`, etc.) — needed to
  rewrite consumption after the shape changes from flat to `{ data: { rootField } }`.

## Step 3 — Skip multi-root / aliased operations up front

If the operation's top-level selection set contains **more than one field** (whether aliased or
not), e.g.:

```graphql
mutation {
  query1: aaa
  query2: bb
}
```

or the `deleteUser0: deleteUser(...) deleteUser1: deleteUser(...)`-style dynamically-built
batch mutations — **do not convert it**. A single generated SDK operation maps to exactly one
named operation with one root field; there's no clean 1:1 target. Leave it as a raw string and
note it as skipped ("multi-root/aliased operation — no single SDK call covers this").

Only single-root-field operations proceed to Step 4.

## Step 4 — Check whether a matching generated SDK operation exists

Search `citest/tools/graphql-api/src/gql/gql.ts` for a method of that exact name inside the
`getSdk(...)` function body:

```bash
grep -n "^    <rootFieldName>(" citest/tools/graphql-api/src/gql/gql.ts
```

- **No match** → skip this operation ("no generated SDK method named `<rootFieldName>`") and
  move on. Do not add one — extending the generated SDK isn't in scope for any skill; it comes
  from the schema via codegen.
- **Match found** → find its `<OperationName>Document` (or the type referenced in the sdk
  method's `Promise<{ data: <X>Query | <X>Mutation ...}>`) and read the corresponding
  `export type <X>Query = { ... }` / the document's `gql\`...\`` body to see exactly what fields
  it selects and what its variables type requires.

## Step 5 — Confirm field coverage before converting

Diff the raw operation's selection set (recursively, including nested selections) against the
matched generated operation's selection set.

- **Fully covered** (generated selects every field the spec reads from the result, or a superset)
  → proceed to Step 6.
- **Missing fields** (the spec reads a field the generated operation doesn't select) → skip this
  operation ("generated SDK operation `<name>` doesn't select `<field>`, which this test reads")
  and leave it as a raw string. Do not attempt to widen the generated document — it's owned by
  codegen, not hand-edited.
- **If genuinely ambiguous** (e.g. unsure whether a nested field is actually read vs. just present
  defensively) — ask the user with `AskUserQuestion` rather than guessing wrong in either
  direction.

## Step 6 — Rewrite the call site in `filePath`

For each operation that passed Steps 3–5:

1. Replace the raw call — `<client>.query(<raw template string>, <maybe variables/null>)` —
   with `<client>.sdk.<rootFieldName>(<variablesObject>)`.
   - Convert any JS-template-interpolated literal arguments (`` name: "${citestMarker} ..." ``)
     into a proper JS object literal for the variables argument, matching the generated
     operation's variables type (e.g. `{ input: { name: `${citestMarker} ...`, clientId:
     'test-client-id', ... } }`). Preserve the original literal values exactly — this is a call
     wiring change, not a test data change.
   - If the raw call already used explicit `$variables` bound to an object the JS code built
     separately, just pass that existing object through instead of the raw string.
2. Update every downstream consumption of the result to go through `.data`:
   - `_.get(result, 'rootField.x.y')` → `_.get(result, 'data.rootField.x.y')`
   - `result.rootField` / `result?.rootField` → `result.data.rootField` / `result?.data?.rootField`
   - `await expect(client.query(query)).rejects.toThrow(...)` →
     `await expect(client.sdk.rootField(variables)).rejects.toThrow(...)` (shape doesn't matter
     for a rejection assertion, only the call itself changes).
   - Keep the same local variable name for the result (`result`, `res`, etc.) so unrelated lines
     stay untouched — only insert `.data` into paths, don't rename variables.
3. Leave everything else in the file — imports, unrelated tests, formatting elsewhere — alone.

## Step 7 — Report

Summarize per operation, referencing line numbers in `filePath`:
- **Converted**: root field, old raw call → new `.sdk.<op>(...)` call.
- **Skipped**: root field (or "multi-root operation" if no single field applies) and the
  specific reason (no matching SDK method / missing field coverage / multi-root selection).

Do not silently drop any raw operation from the summary — every one found in Step 2 must be
accounted for as either converted or skipped-with-reason.

## Step 8 — Verify

Type-check the touched file: `cd citest/tools/graphql-api && npx tsc --noEmit` (pre-existing
unrelated errors elsewhere in the workspace are expected and not this skill's concern — only
check that no *new* errors appear in `filePath`). Also re-read the diff once to confirm no file
other than `filePath` changed.
